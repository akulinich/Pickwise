# Pickwise: план веб-приложения

## 1. Цель

Сделать статическое веб-приложение для расчёта матчей Hearthstone Conquest 4×4 с одним баном. Финальный результат расчёта должен быть доступен в двух формах: как состояние экрана приложения и как скачиваемый PDF. Приложение должно полностью работать в браузере, не требовать сервера и публиковаться через GitHub Pages.

Математическим эталоном служит реализация из `C:\projects\HSAI\hsai\conquest_solver.py`. Представление результата сверяется с `conquest_panel.py`, `conquest_print.py` и исходным описанием в `docs/concuest-promt.md`. Режим живого матча и хранилище истории из HSAI в Pickwise не переносятся.

## 2. Что переносим из HSAI

### Математическая модель

- Пользователь задаёт по четыре колоды и матрицу вероятностей 4×4: `P[i][j]` — шанс моей колоды `i` выиграть одну игру у колоды соперника `j`.
- После фактических банов остаётся Conquest 3×3. Состояние определяется **конкретными множествами** колод, которым ещё нужна победа, а не только размерами этих множеств.
- Для каждого нетерминального состояния строится матрица продолжения:

  `Q[i][j] = P[i][j] × V(S − {i}, T) + (1 − P[i][j]) × V(S, T − {j})`.

- Каждая `Q` решается как конечная нулевая сумма: моя сторона максимизирует вероятность победы в матче, сторона соперника минимизирует её. Результат содержит цену игры и обе смешанные стратегии.
- Динамическое программирование рассчитывает все достижимые состояния постбанового матча (для 3×3 — 63 состояния, включая терминальные; состояние с двумя пустыми наборами не требуется).
- Для каждой из 16 пар банов рассчитывается отдельная игра 3×3. Полученные стартовые значения образуют матрицу банов 4×4, которая снова решается как нулевая сумма.
- Расчёт остаётся детерминированным и использует полную точность; Monte Carlo допустим только как дополнительная проверка, не как способ выбора стратегии.

Важно зафиксировать в новой модели данных понятные имена: строки матрицы банов — **какую колоду соперника баню я**, столбцы — **какую мою колоду банит соперник**. В Python-реализации внутренние имена индексов легко перепутать.

### Пользовательский сценарий

1. Ввести название события/матча, названия и короткие обозначения восьми колод.
2. Ввести проценты в матрицу матчапов 4×4 и запустить расчёт.
3. Увидеть общую вероятность победы, оптимальные смешанные стратегии обоих банов и матрицу результатов для всех пар банов.
4. Просмотреть результаты каждой пары банов и соответствующие таблицы постбановых решений.
5. Нажать **Show math** и проследить вычисления от исходных matchup-процентов до любого итогового значения.
6. Перед созданием PDF проверить наш бан в dropdown: по умолчанию выбрана рекомендация solver, но её можно заменить.
7. Скачать PDF с итогами расчёта и тактическими таблицами для выбранного нашего бана.

## 4. Техническая архитектура

### Рекомендуемый стек

- React + TypeScript + Vite для статического SPA;
- отдельный, не зависящий от React модуль `solver`;
- Vitest для модульных и property-based проверок, Playwright для ключевых пользовательских сценариев;
- обычный CSS с дизайн-токенами; UI-библиотека не нужна до появления реальной потребности;
- GitHub Actions: проверка, production build, загрузка `dist` как Pages artifact и публикация через официальный Pages workflow.

CI/CD workflow запускается при каждом push в `main`: сначала тесты и production build, затем — только при их успехе — автоматический деплой `dist` на GitHub Pages. Для pull request workflow запускает тесты и production build, но ничего не публикует. Также должен быть доступен ручной запуск через `workflow_dispatch` для повторного деплоя или диагностики.

Vite должен собирать ассеты с базовым путём `/Pickwise/`. Для первой версии лучше обойтись без URL-роутера или использовать hash routing, чтобы обновление вложенного адреса не приводило к 404 на GitHub Pages.

### Перенос LP-решателя

`scipy.optimize.linprog` заменяем готовой браузерной библиотекой, а не собственной реализацией simplex.

Основной кандидат — [`yalps`](https://github.com/IanManske/YALPS): небольшой LP/MILP solver на TypeScript под MIT, рассчитанный на малые задачи и работающий в браузере без WASM. Размеры Pickwise намного меньше заявленной области применения: максимум четыре вероятности стратегии плюс переменная цены игры и не более четырёх основных ограничений.

Над библиотекой нужен собственный узкий адаптер `solveMatrixGame(Q)`. Как и Python-эталон, он решает две LP отдельно:

- прямую задачу для моей максимизирующей стратегии;
- двойственную задачу для минимизирующей стратегии соперника.

Значения `Q` всегда находятся в `[0,1]`, поэтому переменную цены можно явно ограничить тем же диапазоном; отсутствие unrestricted variables в YALPS здесь не мешает. Адаптер нормализует малые отрицательные численные остатки, проверяет суммы вероятностей, все ограничения и primal/dual gap.

Резервный вариант — [`highs`](https://github.com/lovasoa/highs-js), браузерная WebAssembly-сборка solver’а HiGHS под MIT. Он функционально сильнее, но для крошечных LP Pickwise тяжелее необходимого и требует корректной публикации `.wasm` с подпути GitHub Pages.

`glpk.js` технически подходит и уже использует Web Worker, но распространяется под GPL-3.0; для MIT-репозитория Pickwise это нежелательный лицензионный выбор. `javascript-lp-solver` также подходит, но YALPS создан как его более лёгкая TypeScript-ориентированная переработка для малых задач.

Перед окончательной фиксацией YALPS делаем короткий spike: прогоняем эталонные и случайно сгенерированные матрицы против Python/SciPy, включая вырожденные случаи, и измеряем полный расчёт 16 постбановых игр. Если численная проверка не проходит, переключаем адаптер на HiGHS без изменения solver API или UI.

### Данные и приватность

- Сервер и база данных для MVP не нужны.
- Входные данные и результат живут только в состоянии открытой страницы.
- После изменения входа старый результат помечается неактуальным до повторного расчёта.
- PDF строится локально в браузере; колоды и matchup-данные никуда не отправляются.
- Сохранение между сессиями, история и синхронизация не входят в MVP.

## 5. Экраны и UX

- **Подготовка:** два состава, быстрые алиасы, удобный селектор Hearthstone-класса с иконками для каждой колоды, матрица 4×4, пресет 50%, явные ошибки около полей.
- **Результат:** общая вероятность победы, две смешанные стратегии банов и тепловая payoff-матрица 4×4.
- **Таблицы решений:** просмотр любой пары банов; для каждого состояния `S,T` показываются вероятность победы в матче и ненулевые вероятности следующего выбора. На узком экране используются карточки/фильтры вместо нечитаемой широкой таблицы.
- **Show math:** кнопка на экране результата открывает полноэкранную панель или отдельный раздел с вычислениями. По умолчанию показывается краткое объяснение итогового значения, но пользователь может раскрыть любую пару банов, состояние и ячейку `Q` вплоть до базовых случаев.
- **Our ban for PDF:** dropdown расположен рядом с кнопкой скачивания и содержит четыре колоды соперника с рассчитанными вероятностями нашего бана. После каждого нового расчёта автоматически выбирается колода с максимальной вероятностью; при точном равенстве — первая по порядку в составе. Пользователь может выбрать любую другую колоду. Переопределение влияет только на PDF/его preview и не меняет оптимальную стратегию solver.
- **PDF:** заметная кнопка скачивания после успешного расчёта. Документ строится для выбранного нашего бана и показывает четыре возможных бана нашей колоды соперником. PDF получает данные из той же нормализованной модели результата, что и экран, чтобы числа и подписи не расходились.

Порог вроде 0,5% влияет только на отображение. Нулевые или скрытые малые вероятности нельзя удалять из внутренней стратегии.

### Что показывает Show math

Режим объяснения должен быть рассчитан на пользователя, который понимает проценты, но не обязан знать линейное программирование.

1. **Правила и обозначения:** что означают `P`, `S`, `T`, `V` и почему после победы исчезает моя колода, а после поражения — колода соперника.
2. **Базовые случаи:** `V(∅, T) = 100%` и `V(S, ∅) = 0%` с объяснением человеческим языком.
3. **Расчёт состояния:** для выбранных `S,T` отображается вся матрица `Q`. Каждая ячейка раскрывается в формулу, подстановку конкретных чисел и результат, например:

   `Q[A,X] = 55% × V(BC, XYZ) + 45% × V(ABC, YZ) = 53,71%`.

4. **Оптимальная стратегия состояния:** показываются обе смешанные стратегии, цена игры и смысл результата. В расширенном блоке — ограничения прямой и двойственной LP, их численные значения и primal/dual gap.
5. **Динамическое программирование:** состояния группируются по `|S| + |T|` и показываются в порядке от базовых к стартовому 3×3. Для каждого состояния доступны `V`, `Q`, стратегии и ссылки на дочерние состояния.
6. **Каждая пара банов:** для всех 16 комбинаций видны оставшиеся колоды, ссылка на соответствующий расчёт 3×3 и его стартовое значение.
7. **Итоговая игра банов:** показывается собранная payoff-матрица 4×4, затем обе оптимальные стратегии банов, общая вероятность победы и расширенная LP-проверка.

«Все вычисления» означает, что ни одно использованное промежуточное состояние или число не скрыто без возможности раскрыть его. Одновременно на экран выводится только выбранная ветка/уровень; нужны оглавление, фильтры, сворачивание секций и ссылки между родительскими и дочерними состояниями. Значения в формулах показываются с удобным округлением, а рядом должна быть возможность увидеть полную машинную точность.

## 6. Проверка корректности

- Перенести существующие тесты HSAI: 1×1, симметричные 50%, детерминированные матчапы, нормализация стратегий, primal/dual ограничения и соответствие ячеек банов стартовым значениям 3×3.
- Сгенерировать Python-эталоном набор JSON fixtures: обычные, вырожденные и граничные матрицы (0%, 50%, 100%). Сравнивать value и допустимость стратегий с оговорённым tolerance.
- Добавить свойства: все значения находятся в `[0,1]`, стратегии суммируются в 1, терминальные состояния верны.
- Проверять экран и PDF на одном fixture: ключевые значения, названия колод, ориентация банов и таблицы должны совпадать.
- Проверять dropdown нашего бана: выбор максимального веса по умолчанию, стабильное разрешение равенства, ручное переопределение и сброс к новой рекомендации после повторного расчёта.
- Для каждого fixture проверять Show math: все 16 пар банов присутствуют, каждая `Q` воспроизводится из дочерних `V`, а отображённые подстановки дают сохранённый результат в пределах tolerance.
- E2E-сценарий: ввод → расчёт → Show math → раскрытие ячейки до базовых случаев → просмотр нескольких пар банов → проверка рекомендуемого нашего бана → ручная замена → скачивание PDF с заменённым баном.
- Добавить визуальную проверку отрендеренных страниц PDF: отсутствие обрезанного текста, наложений и выходов за границы.
- Проверить production build именно с `base=/Pickwise/`, а также клавиатурную навигацию, контраст и мобильные размеры элементов управления.

## 8. Критерии готовности MVP

- Для одинакового входа web solver и Python-эталон дают одинаковую цену игры в пределах согласованного tolerance, а стратегии удовлетворяют ограничениям матричной игры.
- Пользователь вводит исходные данные один раз и получает полный результат расчёта на экране без сервера.
- Из любого итогового значения пользователь может через Show math дойти до исходных matchup-процентов и базовых случаев; формулы воспроизводят фактические данные solver, а не рассчитываются отдельно для показа.
- Перед скачиванием PDF пользователь видит рассчитанный default нашего бана и может заменить его; документ однозначно показывает, для какого нашего бана он построен.
- Скачанный PDF содержит согласованные с экраном исходные данные, стратегии банов и постбановые решения для выбранного нашего бана.
- Все действия доступны с клавиатуры и понятны без знакомства с математикой solver.
- Страница корректно работает по адресу репозитория GitHub Pages и после прямой перезагрузки.
- CI запускает тесты и build; публикация происходит только после успешных проверок.
- Каждый push в `main` автоматически публикует успешно проверенную сборку на GitHub Pages; pull request никогда не выполняет deployment.
- PDF помещается в согласованный формат страниц, остаётся читаемым и не зависит от настроек системного диалога печати.

## 9. Риски

- **Численная корректность LP:** самая высокая цена ошибки; снимается эталонными fixtures, проверкой primal/dual и граничными тестами.
- **Путаница сторон и банов:** снимается явными доменными именами и тестами ориентации матриц.
- **Слишком плотная таблица на телефоне:** нужен отдельный мобильный способ просмотра состояния, а не простое сжатие 7×7.
- **Расхождение экрана и PDF:** оба представления должны строиться из общей модели результата и проверяться одним fixture.
- **Путаница рекомендации и ручного выбора:** рядом с dropdown отдельно показываются оптимальное распределение и фактический выбор для PDF; ручная замена не выдаётся за новую рекомендацию solver.
- **Объём Show math:** полный расчёт содержит сотни состояний и LP-ограничений; решается ленивым рендерингом, иерархией и навигацией без удаления данных.
- **Объяснение расходится с solver:** математический режим не должен повторно реализовывать формулы; solver сохраняет структурированный trace, из которого строится объяснение и который проверяется тестами.
- **Расхождение с HSAI:** Python-версия остаётся эталоном до принятого изменения правил; изменения модели оформляются отдельно и покрываются новыми fixtures.

### Принятые решения

- Язык первой версии: только английский. Локализация и переключатель языков в MVP не входят.
- Аудитория: публичный инструмент для пользователей, уже знакомых с Conquest. Интерфейс остаётся плотным и профессиональным; onboarding, обучающие туры и постоянные подсказки не нужны. Краткие пояснения доступны только по запросу, а подробная математика вынесена в Show math.
- Таблица решений на странице и в PDF: компактная 4×4, только состояния с двумя или тремя оставшимися колодами у обеих сторон. Все одиночные и терминальные состояния продолжают рассчитываться и доступны через Show math.
- Состав PDF основан на HSAI, но перед генерацией пользователь выбирает наш бан из dropdown. Default — колода соперника с максимальной вероятностью в рассчитанной стратегии нашего бана; пользователь может переопределить выбор. PDF содержит выбранный наш бан и четыре блока для каждого возможного бана нашей колоды соперником. В каждом блоке показывается соответствующая компактная таблица постбановых решений.
- Формат PDF: одна страница A4 в альбомной ориентации.
- Ввод MVP: только ручной ввод колод и 16 matchup-процентов. Импорт из файла или HSAI будет отдельным последующим этапом.
- Show math доступен только на странице и не включается в PDF. PDF содержит итоговые стратегии и компактные тактические таблицы без математического разбора.
- Публикация: стандартный адрес `https://akulinich.github.io/Pickwise/`; собственный домен не планируется.
- Визуальный стиль сайта: самостоятельный современный Pickwise, без копирования desktop-интерфейса HSAI. Сохраняются только полезная структура данных и смысловая цветовая индикация.
- Визуальный стиль PDF: повторить текущий лист HSAI, включая его компоновку и оформление.
- Классы колод: перенести текущие Hearthstone class icons из HSAI. Для каждой колоды пользователь явно и удобно выбирает класс; выбор отображается на странице и в PDF. Повторяющиеся классы внутри одного состава разрешены и не вызывают предупреждений.
- Поддерживаемые браузеры: актуальные Chrome, Edge, Firefox и Safari на компьютерах и мобильных устройствах. Поддержка старых браузеров и специальных legacy-полифилов не требуется.
- PWA и гарантированный офлайн-режим не входят в MVP.
- Аналитика не входит в MVP. Существующий GoatCounter подключается отдельным последующим шагом; до этого приложение не загружает внешние аналитические скрипты и не отправляет события.
- Хранение между сессиями и история расчётов не входят в MVP; состояние существует только в открытой странице, итог можно сохранить в PDF.
